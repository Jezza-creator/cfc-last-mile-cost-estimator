# Last Mile

Workspace for building a Snowflake-based CFC last-mile cost forecasting app.

## Setup
- Python 3.13 virtual environment in `.venv`
- Snowflake connection via `~/.snowflake/connections.toml`
- Main connection profile: `tsfpa_app_dev`

## Project Layout
- `app/` - Streamlit app
- `src/` - reusable Python code
- `sql/` - Snowflake SQL
- `tests/` - pytest tests
- `data/inputs/` - local input files
- `data/inputs/box_suite/` - proxy and future CFC box suite files

## Box Suite Workflow

- The estimator reads a proxy box suite from `data/inputs/box_suite/proxy_box_suite_non_cfc.csv` when present.
- The future CFC-specific upload should go into `data/inputs/box_suite/cfc_box_suite.csv`.
- The required schema and upload steps are documented in `data/inputs/box_suite/README.md`.
- Stage 3 logic map and working assumptions are documented in `docs/stage3_cost_estimator_logic_map.md`.

## SKU Variance Report

- `src/profile_cfc_plm_variance.py` compares the current CFC SKU attribute record against PLM dimensions and weight.
- It writes a ranked output to `outputs/cfc_plm_variance_report.csv`.
- It also writes `outputs/cfc_keycode_review.csv`, which is a shorter Ops-facing list of keycodes to check first.
- The top rows are intended for operations review when CFC and PLM disagree on dimensions or weights that could affect shipping cost.

## Validation Outputs

The stage 2 and stage 3 runs now produce two review tables that are meant for different audiences:

- `outputs/stage2_*_parcelizer_validation.csv` shows how the parcelizer split each order. Use this first when you want to check whether the parcel allocation looks sensible.
- `outputs/stage2_*_parcelizer_air_ratio_summary.csv` shows the distribution of fill and air ratio by carrier and pack process.
- `outputs/stage2_*_parcelizer_keycode_review.csv` lists the keycodes from orders with odd parcel allocation or large Shippit-vs-estimated gaps.
- `outputs/stage3_*_carrier_validation.csv` shows how the carrier costing behaved. Use this to compare the actual carrier cost with the cheapest valid alternative.
- Stage 1 uses `KSFPA.OMFP.ORD_FULFILLMENT_DETAIL` as the preferred parcel and keycode source when positive-quantity rows cover the Shippit parcel count. It retains `KSFDA.CATCH_CFC.PACKED` as the fallback for incomplete fulfillment detail, and writes source package/shipment IDs plus `assignment_source` into the Stage 1 outputs for auditability.
- `outputs/invoice_drilldowns/<site>_<invoice>_drilldown.xlsx` combines the parcelizer, cost, and SKU-dimension views for one consignment so Ops can review an order end to end. The UI presents this as the Consignment explorer.
- The Streamlit `Model quality` workspace shows data readiness, parcel-count matching, Shippit-versus-estimator chargeable-weight and cube signals, slices by CFC/carrier/process path, selected-period RBU exposure, flagged keycodes, air-ratio norms, and active assumptions. It also provides CSV downloads for the quality and RBU review lists.
- The `Model quality` workspace is deliberately separate from `Invoice reconciliation`: it can be used with the daily Stage 1-3 outputs, while reconciliation requires carrier invoice data and is used as the later validation feedback loop.
- The Invoice reconciliation workspace has a `Validation dataset` selector. Keep the live rolling 14-day option for recent checks; use an aligned historical snapshot, such as `CP July 2026 validation snapshot` or `Australia Post July 2026 sample snapshot`, when invoices arrive after the 14-day operational window.
- Invoice reconciliation also shows invoice coverage against every selected Shippit consignment. The weekly table is organised by shipped carrier, shipped service, and accounting week, with Shippit consignments, matched consignments, invoice coverage, and modelled-versus-invoiced accuracy.
- The Dashboard `Carrier-choice opportunities` section is a fast, modelled signal for consignments where a valid next-best carrier/service is cheaper on the same Shippit physical basis. Its grouped table is at CFC, current carrier, next-best carrier, and AP pricing zone level; it includes eligible consignment, parcel, unit, total-cost, average-cost, and saving measures. The weight-band filter defaults to all bands and applies to both the table and headline totals. The headline opportunity rate is eligible consignments divided by all Stage 3 consignments in the selected scope. Services remain in the consignment-level CSV export. Savings are not invoice-verified or a commitment to switch carriers; GoBUNDLE proxy pricing is excluded. Before acting, investigate each CFC's WHS parcel-count and chargeable-weight logic, how WHS configures carrier ratecards and carrier choice, and whether Shippit's chargeable weight reflects the same basis. Approved, investigated items should be promoted separately into the persistent opportunity register.
- The `Historical trends` workspace contains the complete weekly history and trend view sourced from the combined persisted history. Select one or more accounting weeks, then choose estimator or invoiced actual cost, cost per consignment, cost per parcel, cost per unit, CPU, variance, or invoice coverage. The first matrix row is the aggregate invoice-verified percentage for the selected scope.
- The historical lane and weight matrix uses invoice-verified consignments from the selected weeks only. It supports the same volume and modelled-cost measures as the operational matrix, including percentage-of-total views and weighted cost-per-consignment, cost-per-parcel, and cost-per-unit totals.
- Historical trends also includes `Air and packaging diagnostics`. It compares invoiced actual cube/dead weight where available, otherwise Shippit, against the Stage 3 packed SKU cube and weight. The directional opportunity estimates the value of reducing volume-led chargeable weight toward the mean air share for each CFC, shipped carrier, and service cohort, and the ranked outlier list can be downloaded for Ops investigation.
- The Invoice reconciliation workspace includes a second weekly cost/CPU matrix. It defaults to variance percentage and can show matched modelled cost, modelled CPU, invoiced actual cost, invoiced actual CPU, variance amount, or variance CPU. CPU is cost per packed Shippit unit and is calculated only from matched invoice records with a complete units denominator.
- The Invoice reconciliation workspace also shows a fast carrier/CFC dim/weight variance signal from the saved reconciliation summaries. It reports total observed variance, the signed variance assigned to Shippit cube and/or chargeable-weight mismatch, and the residual. This is directional evidence for triage; use the detailed loader for invoice-level attribution. A signed dim/weight contribution can exceed 100% when another driver offsets it.
- The Reporting period control includes `Single accounting week`. Use it before loading detailed reconciliation to reduce the invoice-level scope and keep large carrier datasets responsive; the high-level summary remains based on the selected saved validation dataset.
- After loading matching reconciliation records, the workspace shows an exclusive Shippit dim/weight diagnostic. It separates cube-and-weight, weight-only, cube-only, no-material-mismatch, and unavailable-evidence cohorts, with observed cost variance and physical comparison measures.
- The residual model and rate view is restricted to the no-material-Shippit-dim/weight-mismatch cohort. This is a controlled comparison of estimator/rate performance, not a counterfactual repricing of records where the carrier invoice dimensions/weight differs from Shippit; the original bridge remains the complete observed variance.
- The consignment coverage export retains matched, matched-by-tracking-number, and not-yet-matched rows. The reconciliation files panel shows which carrier feeds are available to the selected validation dataset, so missing invoice coverage is distinguishable from zero variance.
- Persisted coverage retains estimator cube and chargeable weight, Shippit cube and weight, and invoiced actual chargeable weight and cube as separate physical measures. This supports long-term testing of whether the estimator is a better predictor of eventual invoice chargeable weight than Shippit in particular cohorts.
- In the `All carrier history` view, the detailed variance bridge uses the same persisted coverage keys as the weekly matrices and resolves them against both current and archived carrier reconciliation extracts. This keeps the bridge population aligned with the weekly matched-consignment totals after historical files have been rolled forward.

It writes `outputs/reconciliation_store/live/consignment_invoice_coverage.csv`, `weekly_invoice_summary.csv`, and `manifest.csv`; the normal build matches only the refreshed rolling-window consignments and upserts them while retaining older rows.

This is intentionally slower and should be reserved for backdated corrections, matching-logic changes, or a controlled audit.

The weekly script runs every Monday by default. Do not add `-WithInvoiceReconciliation` to the normal daily task unless invoice feeds are intentionally being processed that day.

It discovers the live store, the existing combined store, and archived coverage stores under `outputs/carrier_invoice_snapshots/`, then prefers matched records when the same consignment appears in more than one source.

How to read the parcelizer validation table:

- `parcel_count_match = Y` means the estimated parcel count matched the actual parcel count.
- `flag_odd_allocation = Y` means the parcel split looks unusual and should be reviewed.
- `est_parcelization_scope` separates single-parcel invoices from multi-parcel invoices.
- `est_pack_process_group` rolls the detailed parcelization method into a smaller set of review-friendly groups.
- `shippit_dead_weight_kg`, `shippit_volumetric_weight_kg`, and `shippit_chargeable_weight_kg` show the consignment basis from Shippit.
- `avg_weight_gap_kg` and `avg_chargeable_gap_kg` show how far the model is from the shipped result.
- Large gaps mean the physical split likely needs work before the carrier economics can be trusted.
- Couriers Please is treated as an invoice-level carrier in the cost model: the billing weight is rounded up to the next whole kilogram and the drilldown shows that rounded invoice basis explicitly.
- Allied ROAD is treated as consignment-level billing: the combined estimated chargeable weight is rounded up to the next whole kilogram and priced once for the consignment. Parcel-level dimensions remain available for operational and oversize assessment.
- Allied base rates are loaded from `data/reference/allied_ecom_cfc_ratecard.csv`, a normalized copy of the proposed ECOM Road/Standard/Oversize Pallet sheet issued 6 July 2026. The file carries separate Sydney/`MOOREBANK` and Melbourne/`TRUGANINA` origins, so the corresponding `N01` and `V01` CFC rate columns are used. `2026-07-06` is the ratecard issue-date assumption, not a confirmed contractual effective date; confirm this with Allied before treating it as final. The previous B2C CSV remains available as a fallback if the normalized file is absent.
- Effective-dated carrier fuel surcharge inputs are maintained in `data/reference/carrier_fuel_surcharge_rates.csv`. The Streamlit **FSC model inputs** workspace preloads the published schedule, allows one row per carrier/service/date range to be edited, and shows the invoice-validated weighted average beside each model rate. The validation value is read-only evidence and never drives Stage 3. Save the schedule, then rerun both Stage 3 scripts for the new assumption to take effect; existing reconciliation files are not rewritten by the workspace.
- The drilldown also flags when a Couriers Please order exceeds the 10-parcel review cap so Ops can tell when the carrier assumption needs a closer look.

How to read the air-ratio summary:

- `avg_fill_pct_vs_shippit_cube` shows how full the estimated parcels are compared with the Shippit volumetric cube.
- `avg_air_ratio_pct_vs_shippit_cube` shows the average amount of air in the cartons.
- `p25` and `p75` help show the normal operating range.
- `outlier_invoice_count` shows how many invoices sit outside the usual band and may deserve a closer look.
- `est_air_ratio_review_flag` and `est_outlier_review_flag` help spot groups that are unusually airy, unusually tight, or too noisy to trust without review.

How to read the keycode review tables:

- They are deliberately shorter than the main variance outputs.
- The PLM keycode review highlights SKUs where CFC and PLM disagree enough to matter.
- The parcelizer keycode review highlights SKUs appearing in orders with unusual parcel splits or big Shippit comparison gaps.
- The review outputs now keep single-parcel and multi-parcel invoices separate so Ops can check dimension issues before split-logic issues.
- The review tables now include a short `review_commentary` column so the main takeaway is visible without reading every metric first.
- The consignment drilldown workbook adds a plain-English summary, parcel validation, parcel detail, cost detail, and SKU review so an Ops user can check a Shippit consignment number from top to bottom.
- The SKU review intentionally avoids calling out PLM gaps for apparel-like keycodes, because PLM coverage is not always expected there.
- The intent is to give Ops a practical starting list, not a final verdict.

How to read the carrier validation table:

- `shippit_carrier` and `shippit_service` show the shipped carrier/service being reviewed.
- `est_cheaper_option_pct` shows how often a cheaper valid carrier/service existed.
- `est_avg_actual_cost_ex_gst` is the modelled actual carrier cost.
- `est_avg_cheapest_alt_cost_ex_gst` is the best available alternative.
- If the actual cost is consistently higher than the cheapest alternative, the costing rules or carrier coverage likely need review.

These outputs are intentionally a starting point.

- The goal is to make the logic visible enough that Ops can question it, not to treat the first-pass answer as final.
- If the parcelizer or carrier validation shows repeated gaps, that is a signal to improve the logic, the source data, or the carrier assumptions.
- Practical feedback from Ops is expected and welcome because the model should get better as the business validates it.
- Fallback means the model used the next-best explainable rule because the cleanest signal was missing or ambiguous.

## Carrier Invoice Ingestion

- Place Couriers Please `.xlsx` invoice exports in `data/inputs/carrier_invoices/couriers_please/`.
- Run `./.venv/Scripts/python.exe -m src.carrier_invoice_cp_ingest` to create the reconciliation-ready charge-line file and file-level controls.
- The CP importer reads every worksheet with a `Consignment Ref.` header and ignores workbook summary/configuration sheets. It de-duplicates repeated consignment references across weekly and consolidated workbooks, preferring rows from a consolidated `FY2027 Courier Please Kmart...` workbook. `.xlsb` files are not currently supported.
- The import preserves each CP billed consignment and writes `outputs/carrier_invoices/couriers_please_charge_lines.csv` plus `outputs/carrier_invoices/couriers_please_invoice_control_summary.csv`.
- `carrier_tracking_number` is the CP consignment reference and `kmart_invoice_number` is taken from CP's `Customer Other Reference 1`, allowing the next reconciliation step to match both tracking and Kmart consignment identifiers.
- Run `./.venv/Scripts/python.exe -m src.carrier_invoice_cp_reconciliation` after Stage 3 to compare billed CP consignments with modelled CP costs for both CFCs.
- The reconciliation uses the CP tracking number first and only falls back to Kmart invoice number when that is unambiguous. It writes `outputs/carrier_invoices/couriers_please_reconciliation.csv`, `outputs/carrier_invoices/couriers_please_reconciliation_summary.csv`, `outputs/carrier_invoices/couriers_please_dimension_diagnostics_summary.csv`, and `outputs/carrier_invoices/couriers_please_reconciliation_cost_bridge.csv`.
- CP invoice `PWF0`, `PWF1`, `PWF3`, and `PWF5` service codes are explicitly mapped to the estimator's `PA0`, `PA1`, `PA3`, and `PA5` pricing families. The reconciliation detail exposes both `actual_cp_service_family` and `cp_service_mapping_status` so this comparison is auditable; unknown PWF codes remain `NOT_MAPPED`.
- CP reconciliation uses `SHIPPIT_PHYSICAL_BASIS_MISMATCH` when the carrier and Shippit have a material cube and/or chargeable-weight difference. Detail retains `SHIPPIT_CUBE_UNDERSTATED`, `SHIPPIT_CUBE_OVERSTATED`, and `SHIPPIT_CHARGEABLE_WEIGHT_MISMATCH`, together with carrier, estimator, and Shippit measurements and signed gaps.
- Place Allied weekly workbook exports in `data/inputs/carrier_invoices/Allied/` without changing their worksheet structure. Run `./.venv/Scripts/python.exe -m src.carrier_invoice_allied_ingest` to preserve every billed charge line and create job-level inputs. For a Finance-period archive, select the exact worksheets explicitly, for example: `./.venv/Scripts/python.exe -m src.carrier_invoice_allied_ingest --sheet P1W1 --sheet P1W2 --sheet P1W3 --sheet P1W4 --sheet P1W5 --sheet P2W1 --sheet P2W2 --sheet P2W3`.
- Allied charge lines remain at source-row grain for auditability, while `allied_jobs.csv` aggregates each `docket` plus `job_number` across the selected worksheets. This retains later excess-weight, fuel, delivery, or correction charges against the original job instead of treating them as separate ambiguous jobs; `source_sheet` records every contributing worksheet. The invoice control summary remains worksheet-level for completeness checks.
- Run `./.venv/Scripts/python.exe -m src.carrier_invoice_allied_reconciliation` after Stage 3. It matches Allied `Docket` to the Stage 3 carrier tracking number first; `Reference = Order <external order id>` is only an unambiguous fallback, since fulfilment-order suffixes are not fixed.
- Allied reconciliation writes `outputs/carrier_invoices/allied_reconciliation.csv`, `outputs/carrier_invoices/allied_reconciliation_summary.csv`, `outputs/carrier_invoices/allied_reconciliation_cost_bridge.csv`, and `outputs/carrier_invoices/allied_fuel_norms.csv`. It separately exposes Allied base, excess-weight, delivery, fuel, and other charge components; modelled fuel is an invoice-derived p50 assumption, with a global fallback until a site-zone-service slice has 30 matched jobs.
- To reconcile a historical invoice period while retaining a rolling live UI, point reconciliation to an archived Stage 3 snapshot, for example: `./.venv/Scripts/python.exe -m src.carrier_invoice_allied_reconciliation --moorebank-stage3 outputs/carrier_invoice_snapshots/<label>/stage3_moorebank_cost_estimates_full.csv --truganina-stage3 outputs/carrier_invoice_snapshots/<label>/stage3_truganina_cost_estimates_full.csv`.
- Place GoPeople `.xlsx` invoice workbooks in `data/inputs/carrier_invoices/GoPeople/`. Run `./.venv/Scripts/python.exe -m src.carrier_invoice_gopeople_ingest` to retain carton-level charges and create consignment-level invoice totals, then run `./.venv/Scripts/python.exe -m src.carrier_invoice_gopeople_reconciliation`.
- GoPeople uses `Consignment Number` as the primary tracking key. Matching additionally checks despatch date and destination when a tracking number is reused. Outputs are `gopeople_reconciliation.csv` and `gopeople_reconciliation_summary.csv` under `outputs/carrier_invoices/`.
- GoPeople's `Invoice Notes/Comments/Fuel` field is a dollar fuel amount, not a percentage. Ingest subtracts it from the invoice charge to expose base and fuel separately, and calculates the implied invoice FSC percentage for validation against the effective-dated GoPeople schedule.
- The GoEXPRESS ratecard publishes bands through 20 kg. Stage 3 applies the top published band to a parcel above that ceiling so it remains costed, and exposes `goexpress_weight_cap_applied`, `goexpress_published_max_weight_kg`, and `goexpress_weight_cap_note` for audit. This is an explicit assumption to confirm with GoPeople.
- GoPeople reconciliation uses the same `SHIPPIT_PHYSICAL_BASIS_MISMATCH` primary bucket for material carrier-versus-Shippit cube and/or chargeable-weight differences. The detail output includes carrier, independent estimator, and Shippit cube values, signed kg/m3 gaps, directional diagnostics, and the underlying `root_cause` values.
- Australia Post eParcel invoices are available directly from `KSFPA.ONLINE_UGAM_PVT.OF_INV_AUSPOST`, so no CSV export is required. Run `./.venv/Scripts/python.exe -m src.carrier_invoice_australia_post_ingest --start-date YYYY-MM-DD --end-date YYYY-MM-DD` to create `australia_post_charge_lines.csv`, `australia_post_consignments.csv`, and `australia_post_invoice_control_summary.csv` under `outputs/carrier_invoices/`.
- The AP ingestion treats `B48`, `B5S`, and `B5R` as base service lines; `D05` and `DS1` as fuel surcharge lines; and all remaining materials as other charges. For matched tracking groups, the AP fuel field on the base service row is used as the consignment-level fuel amount. Assignment-level `D05`/`DS1` rows remain explicitly unallocated rather than attaching the full assignment charge to a selected tracking number; the output exposes the fuel line, fuel field, and allocation status separately.
- AP physical measurements are deduplicated by `article_id` and summed to `consignment_id`; financial charge amounts remain at source-line grain. The consignment output retains article counts, duplicate counts, maximum-versus-summed cube and weight controls, and an explicit `MAX_WITHOUT_ARTICLE_ID` fallback for groups without article identifiers.
- Run `./.venv/Scripts/python.exe -m src.carrier_invoice_australia_post_reconciliation` after the relevant Stage 3 run. For historical AP dates, pass archived Stage 3 files with `--moorebank-stage3` and `--truganina-stage3`; the live Stage 3 outputs intentionally remain a rolling 14-day window.
- AP reconciliation writes `australia_post_reconciliation.csv`, `australia_post_reconciliation_summary.csv`, `australia_post_dimension_diagnostics_summary.csv`, `australia_post_reconciliation_cost_bridge.csv`, and `australia_post_fuel_norms.csv`. Where an effective-dated AP FSC rule exists in `data/reference/carrier_fuel_surcharge_rates.csv`, reconciliation uses the Stage 3 published FSC rule; otherwise it falls back to an invoice-derived p50 fuel-to-base assumption. Every prediction is labelled as an assumption; p10/p90 are not used in the model.
- AP detail retains both the source zone codes (`actual_lodgement_zone`, `actual_destination_zone`) and the Stage 3 area/pricing values (`modelled_ap_zone`, `modelled_ap_pricing_zone`). A source code versus descriptive area is marked `NOT_COMPARABLE_SOURCE_CODE_VS_MODEL_AREA` instead of being incorrectly classified as a zone mismatch.
- Stage 3 resolves AP pricing from the CFC origin: Moorebank uses Sydney-origin categories, while Truganina uses Melbourne-origin categories. This means Victorian destinations are `Same State ...` and NSW destinations are `Near State ...` for Truganina. If Melbourne-origin AP coverage is not yet present in Snowflake, the Sydney rate tables are used only as a controlled fallback while the origin-aware category mapping is retained.
- The AP cost bridge uses `SHIPPIT_PHYSICAL_BASIS_MISMATCH` when AP and Shippit have a material cube and/or chargeable-weight difference. The detail keeps the directional cube cause (`SHIPPIT_CUBE_UNDERSTATED` or `SHIPPIT_CUBE_OVERSTATED`) and `SHIPPIT_CHARGEABLE_WEIGHT_MISMATCH`, alongside the AP, Shippit, and independent estimator measurements. The bridge bucket is a primary row attribution, not a claim that every dollar in the row is caused by only one physical measure.
- For a one-off AP validation, run `./.venv/Scripts/python.exe -m src.carrier_invoice_australia_post_sample --start-date 2026-07-15 --end-date 2026-07-31 --sample-size 1000`. The sampler first joins AP tracking numbers to historical Shippit orders, allocates the target across CFC, AP service, weight band, and service-week strata, fetches only the selected AP charge lines, runs targeted Stages 1-3, and reconciles into `outputs/carrier_invoice_snapshots/australia_post_sample_<start>_<end>_<size>/`. Use `--prepare-only` to select and ingest without running the model.
- The AP sample workflow is isolated from the live rolling outputs. Its `stage_outputs` folder contains the filtered Stage 1-3 inputs and outputs, while the parent folder contains the AP charge lines, sample manifest, reconciliation detail, summary, diagnostics, cost bridge, and fuel norms.
- `actual_less_modelled_cost_ex_gst` is positive when CP billed more than the model. Unmatched and ambiguous records are intentionally retained for review rather than being silently excluded.
- The normal operational extraction defaults to the latest seven days. Use `LM_EXTRACTION_START_DATE` and `LM_EXTRACTION_END_DATE` for a deliberate historical run, for example `$env:LM_EXTRACTION_START_DATE = '2026-06-29'; $env:LM_EXTRACTION_END_DATE = '2026-08-23'`. The end date defaults to today when it is not set.
- Before replacing a historical Stage 3 run, archive the current reconciliation inputs and outputs with `./.venv/Scripts/python.exe -m src.carrier_invoice_snapshot --label cp_july_2026`. Snapshots live in `outputs/carrier_invoice_snapshots/` and let us reproduce a past reconciliation without retaining historical data in the live UI.
